## xv6

> > Unix V6을 기반으로 만들어진, 간단한 기능만을 포함한 운영체제이다.

- `모놀리식 커널` 전체 운영체제가 커널 내에 존재하여 모든 시스템 콜의 구현이 커널 모드에서 실행되도록 하는 것
- 6000줄 코드(c언어 대부분, 어셈블리어 300줄)
- RISC, x86 (64bit)
- 32개의 register + pc

  - `zero`
  - `ra` : 함수가 call 되면 (스택 대신) ra에 저장, return 명령어는 ra에 저장된 값을 pc로 복사 -> 메모리에 접근할 필요가 없다!
  - `sp` stack pointer
  - `tp` thread pointer (코어 번호) - 커널 코드에선 바뀌지 않는다.
    - kernel이 user code로 갈 때, 모든 register를 저장한다. (이 때 user code는 tp register의 값을 변경시킬 수 있다!) 그리고 다시 kernel mode로 돌아올 때, 모든 register를 다시 복원한다.
  - `gp` global pointer (complier가 사용하며 바뀌지 않음)
  - `a0`~`a7` 함수에게 argument 전달
  - `t0`~`t6`
  - `s0`~`s11` callee-saved register
    - 함수는 이 레지스터를 사용하기 전에 스택에 저장하고, return하기 전에 복원해야 한다.

- RISC-5 모드
  - machine mode
    - startup+initialization, timer interrupt
  - supervisor mode
  - user mode
    - user mode에서 수행 불가능한 instruction은 trap+abort를 발생시킨다.

## devices

`UART` keyboard로부터 printing, reading input을 받는 통신 채널 제공 (byte stream)
`DISK` 컴퓨터 디스크를 따라가는 1개의 디스크 존재
(UART와 DISK는 코어끼리 공유)
`Timer interrupt` 각각의 코어가 가짐.(local)
`PLIC(Platform Level Interrupt Controller)`각종 device로부터의 interrupt를 관리. (어떤 코어가 interrupted 됐는지 등)

- `Page table`
  - 1 page table / kernel (모든 core가 공유),
  - 1 table / process
- 3 level page table
- Page size = 4KB (fixed)
- virtual address size = 256GB(2^38bit)

- `single free list`(사용되지 않은 pages) : 메모리가 필요하면 여기서 할당되거나 다시 반환됨
- No objects, malloc

## Scheduler

`Round Robin`  
:각 프로세스의 timeslice의 크기는 고정 (1,000,000 cycles)
모든 코어는 1개의 Ready Queue(ready list, run list)를 공유
코어가 ready queue에서 다음 실행할 process를 결정. (time slice가 끝나면 ready queue로 return)

- 각 코어가 반복적으로 ready queue를 탐색하며 실행 가능한 process 찾음.
  <br>

## Boot sequence

`QEMU` loads kernel code at fixed address, starts all cores running.

## Locking

`Spin locks`
(0 : lock is free, 1 : lock is busy)

1. acquire : lock이 0이 될 때까지 기다리고, 1로 바꿈
2. release : lock을 0으로 바꿈

`sleep()` 특정 스레드가 sleep 함수를 사용하면, timeslice를 끝내고 ready queue에 not runnable 상태로 돌아옴.
`wakeup()` 특정 스레드가 wakeup 함수를 사용하면, sleep/block 상태에서 runnable상태로 바뀜.

interrupt를 선택적으로 불가능하게 하여 코어에서 실행 중인 스레드가 방해 받지 않음.

각 코어는 status control word를 가짐.

## User Address Space

(그림)
kernel이 virtual address space를 만들고, stack의 page에 argv, argc 등의 argument를 push.

user program이 실행되면 이 argument들을 stack에서 찾을 수 있다.

- UNUSED:
  아직 프로세스가 생성되지 않았거나, 종료된 프로세스의 자원이 아직 해제되지 않았을 때

- EMBRYO:
  EMBRYO 상태의 프로세스는 생성되었지만 초기화되지 않은 상태입니다. 프로세스가 생성되고 초기화되는 동안 해당 상태가 설정됩니다. 초기화가 완료되면 EMBRYO 상태에서 다른 상태로 전이됩니다.

- SLEEPING:
  SLEEPING 상태의 프로세스는 특정 이벤트가 발생할 때까지 대기하고 있는 상태입니다. 예를 들어, 파일 I/O 완료를 기다리는 경우나 특정 시간이 지날 때까지 대기하는 경우에 해당합니다.

- RUNNABLE:
  RUNNABLE 상태의 프로세스는 실행 가능한 상태이며, CPU를 할당받을 준비가 된 상태입니다. 즉, 다른 프로세스가 CPU를 사용하고 있지 않을 때 실행될 수 있는 상태입니다.

- RUNNING:
  RUNNING 상태의 프로세스는 현재 CPU를 사용하고 실행 중인 상태입니다. CPU를 할당받아 코드를 실행하고 있는 상태를 나타냅니다.

- ZOMBIE:
  ZOMBIE 상태의 프로세스는 종료된 상태이지만, 부모 프로세스가 종료 상태를 확인하기 위해 대기 중인 상태입니다. 이러한 상태는 프로세스의 자원이 완전히 해제되기 전까지 유지됩니다.

`p->pgdir`는 프로세스의 페이지 테이블을 x86 하드웨어가 예상하는 형식으로 보유
`p->kstack` 커널 스택
`p->pagetable` holds the process’s page table, in the format that the RISC-V hardware expects.
(pagetable은 하드웨어에 구현되어 있다.)

## Traps

cpu가 하던 일을 멈추고 handler 코드를 수행하게되는 3가지 경우가 있다.

- `System call` ecall instruction
- `Exceptions` synchronous
  - program error (illegal instruction, alignment error, page fault)
- `Interrupts` asynchronous

  - software interrupt : caused by machine mode, whenever a timer interrupt. Handled by the kernel.
  - I/O

TRAMPOLINE = user 가상 주소 TRAPFRAME

### Locking

아래의 경우에 여러 프로세스가 공유 자원에 동시에 접근하는 `race condition`이 발생할 수 있다.

- 멀티프로세싱 : 여러 프로세스가 공유 data에 접근
- 단일프로세싱 : context switching을 통해 instruction이 interleaved 될 때
- interrupt handler가 interrupt 전후 코드와 같은 데이터를 수정하는 경우
- 두 개의 CPU가 동시에 kalloc하는 경우

### xv6의 해결방법 (lock)

1. `spinlock`
   > mutual exclusion을 위한 lock으로서, struct spinlock의 locked를 1로 만들어 lock을 획득하는 방법이다.

p->lock protects other things as well: the interplay between exit and wait, the machinery to
avoid lost wakeups (see Section 7.5), and avoidance of races between a process exiting and other
processes reading or writing its state (e.g., the exit system call looking at p->pid and setting
p->killed (kernel/proc.c:611)). It might be worth thinking about whether the different functions
of p->lock could be split up, for clarity and perhaps for performance.

먼저, 아래와 같은 방식을 생각해보자.

```c
void
acquire(struct spinlock *lk){
  for(;;) {
    if(lk->locked == 0) {
    lk->locked = 1;
    break;
    }
  }
}
```

위의 방법은 멀티프로세서에서의 mutual exclusion을 만족하지 못한다. 여러 CPU가 동시에 lock을 acquire할 수 있기 때문이다.
RISC-V에는 위의 if문을 atomic하게 해주는 instruction이 있다. (레지스터와 메모리주소를 atomic하게 swap한다.) 이는 아래의 `xchg` 메소드를 통해 가능하다.

```c
void
acquire(struct spinlock *lk)
{
  pushcli(); // disable interrupts to avoid deadlock.
  if(holding(lk)) // 현재 프로세스의 spinlock 보유 여부
    panic("acquire");

  // spinlock이 해제되면 (0이 되면) 무한루프 빠져나오고 locked를 1로 바꿈. busy waiting 발생
  while(xchg(&lk->locked, 1) != 0)
    ;

  // Tell the C compiler and the processor to not move loads or stores
  // past this point, to ensure that the critical section's memory
  // lock을 획득한 후에 critical section에 접근하도록 보장함
  __sync_synchronize();

  // Record info about lock acquisition for debugging.
  lk->cpu = mycpu();
  getcallerpcs(&lk, lk->pcs);
}
```

위 방식은 mutual exclusion을 보장한다.
빠르게 lock을 획득해야 하거나, 짧은 critical section에서 유용하다.(아래 1번 이유)

그러나 아직 문제가 있다.

문제1.lock을 오랫동안 점유해야하는 경우가 있을 수 있다. (file locked when read/write) 이 때 lock을 획득하고자 하는 다른 프로세스는 위의 while문에서 기다리며 계속 cpu를 사용하기 때문에 `busy waiting`이 발생한다.

문제2.또한 spinlock을 획득하는 동안 cpu를 `yield`를 할 수 없는데, 그 이유는 다음과 같다.
첫째, A프로세스가 lock을 해제하지 않은 상태에서 yield를 하게 된다면, B프로세스가 lock을 획득하려고 할 때 이미 A프로세스가 lock을 점유 중이다. 이 때 A는 B에게 yield하여 기다리고 있고, B는 A가 lock을 해제하기를 기다리는 `deadlock`이 발생하게 된다.

둘째, lock이 점유 중일 때 yield를 통해 interrupt가 발생하면 lock을 점유한 프로세스가 아직 작업을 완료하지 않은 상태에서 interrupt가 발생한 것이므로 mutual exclusion을 보장할 수 없다.

따라서 busy waiting을 하지 않으면서, cpu를 yield하고자 한다면 아래의 sleep-lock 방식을 사용할 수 있다.

   다른 프로세스가 락을 해제할 때까지 일시 중지 상태로 대기한다. (cpu점유 X)

1. sleep, wakeup을 통해 I/O를 기다리거나, child의 exit을 기다리는 상황에서 context switching

### context switching 과정

스케줄러는 CPU마다 thread (saved registers, stack)로서 존재한다. (그렇지 않으면 스케줄러가 이전 프로세스의 kernel stack에서 실행해야 하는데 이것은 안전하지 않기 때문. 이 때 다른 코어가 프로세스를 깨우고 실행하면 서로 다른 코어에서 같은 stack을 사용하게 되므로 위험.)

(사진)

전반적인 과정은 아래와 같다.

1. system call / interrupt
   이전 프로세스의 `kernel thread`로 이동

2. kernel thread는 `CPU scheduler thread`로 swtch를 하여 이전 프로세스의 context를 struct proc, cpu의 struct cpu 내에 저장하고 scheduler context로 간다.

3. 새 프로세스의 kernel thread로 swtch

4. 새 user 프로세스로 trap return

이 때 2번 과정을 자세히 살펴보자.

- usertrap에서 yield를 한다. 이 때 interrupt의 과정 끝이 난다.
- yield 내에서 sched 호출 (여기서 cpu 포기)
- swtch호출
- cpu->scheduler로 return한다. (이전에 저장되어 있던)

`swtch`
swtch의 argument로 old와 new가 있다.
`struct context *old`에 현재 context를 저장하고,  
 `struct context *new`에 불러올 context를 저장한다.

- p->context를 저장하고 cpu->scheduler에 저장되어 있는 scheduler의 context를 불러온다. (이전 scheduler가 switch로 저장했던 것)
- thread에 대해 잘 모른다. struct context에 담긴 레지스터들을 저장하고 불러올 뿐.
- callee-saved register들만 저장한다.(필요하다면 caller-saved register들은 c코드에 의해 stack에 저장된다.)
- pc 대신 ra레지스터(swtch가 불린 곳의 return address) 저장
- return 시 ra레지스터가 가리키는 instruction
  (new thread가 swtch를 불렀던 instruction)으로 간다.
  sp는 현재 cpu scheduler stack을 가리키게 된다.

## scheduling

`scheduler`은 각 cpu마다 thread의 형태로 존재.

cpu를 양보하고자 하는 프로세스는 p->lock을 획득해야 하고,(lock을 획득했기 때문에 interrupt는 disabled 되어야.)갖고 있는 모든 lock을 풀어야 하고, p->state를 업데이트하고, sched함수를 호출한다. (yield, sleep, exit도 이 과정) sched에서는 이 조건을 double check.

- lock의 control은 새로운 process에게 넘어간다.

프로세스마다 고정값이 false면 p->lock을 갖고있는다.
ex) p->state가 RUNNING이면,
p->state가 RUNNABLE이면, p->context가 process의 레지스터를 가지고 있어야 한다.
다른cpu가 process의 kernel stack에서 실행되지 않아야

scheduler가 부른 swtch가 sched로 이어지지 않는 한 가지 경우가 있다. 새로운 프로세스가 처음 스케줄링 되면, forkret(p->lock을 release)에서 시작한다. 그 외 프로세스는 usertrapret에서 시작한다.

### myproc

```c
struct proc*
myproc(void) {
  struct cpu *c;
  struct proc *p;
  pushcli(); // 현재 cpu의 interrupt disable
  c = mycpu();
  p = c->proc;
  popcli(); // interrupt enable
  return p;
}
```
